### Headers  

<ParamField header="x-workspace-id" type="string" required>
  Workspace identifier for the API.
</ParamField>

### Request Body

<ParamField body="to" type="string" required>
  The phone number to which the call will be made.
</ParamField>

<ParamField body="call_agent_id" type="string" required>
  The ID of the agent assigned to make the call. Required unless you send `call_flow_id` instead.
</ParamField>

<ParamField body="call_flow_id" type="string">
  The ID of the call flow to call with, accepted in place of `call_agent_id`. The call runs on the agent that the call flow belongs to, and the portal lists both IDs together, so you can send whichever one you have.

  Send one or the other. Sending both is allowed only when they refer to the same agent; if they do not, the request is rejected.

  The call flow must be the live one for its agent. An archived or inactive call flow is rejected rather than silently falling back to the agent's current call flow.
</ParamField>

<ParamField body="from_phone_number_id" type="string" optional>
  The ID of the phone number to call from. When omitted, one of the agent's numbers is chosen automatically.
</ParamField>

<ParamField body="callback_url" type="string" optional>
  A URL to receive webhook events about the call. If provided, this URL will be used for notifications.
</ParamField>

<ParamField body="dynamic_variables" type="object">
  Values to fill in on this call, as a flat object of strings. The keys are your own: there is no fixed list, so name them to match what your call flow uses.

  To use a value, write its key in double curly braces, such as `{{first_name}}`, in any of these call flow settings:

  - the call flow prompt
  - the greeting, as either the custom message or the AI greeting prompt. Calls placed with this endpoint use the call flow's Outbound greeting.
  - the voicemail message

  Spell each key exactly as you send it, including upper and lower case, and put no spaces inside the braces. A `first_name` key fills in `{{first_name}}`, but not `{{firstName}}`, `{{First_Name}}` or `{{ first_name }}`.

  Send every variable your greeting and voicemail use: a missing one is spoken as written.

  The request example on this page suits a call flow whose Outbound greeting is the custom message `{{greeting_text}}`, whose voicemail message is `{{voicemail_message}}`, and whose prompt refers to the person as `{{first_name}}`. Because the text is sent per call, each call can have its greeting and voicemail in a different language.
</ParamField>

<ParamField body="metadata" type="object" optional>
  Any fields passed here will be sent to the call agent and directly passed to the webhook triggered by the agent under its 'metadata' header, but they will not be included in the call agent's context.
  <Expandable title="Metadata Details">
    
  </Expandable>
</ParamField>

<ParamField body="reject_outside_hours" type="boolean" default="false">
  Refuse the call, instead of queueing it, when the call flow is outside its calling hours. The hours are checked when the request is received and again when the call is about to dial:

  - If the call flow is outside its hours when the request is received, the API returns 409 with code `OUTSIDE_CALLING_HOURS`. No call is queued and nothing is added to Call History.
  - If the hours close before the call dials, the call is marked Failed in Call History with `callEndReason` `outside_calling_hours`, and it is not queued again.

  With the default, `false`, a call outside calling hours is queued for the next window. See [Calling hours](#calling-hours). Calls from a WhatsApp number do not use calling hours, so this option does not affect them. Send `true` or `false`; any other value returns 400.
</ParamField>

### Calling hours

When the call flow has calling hours turned on, a call requested outside them is queued by default and dials when the next window opens. Until then it shows in Call History as Scheduled, with the reason "Outside office hours", and its call history record has `status` `pending` and `pendingReason` `office_hours`. If no window opens in the next 30 days, the call is marked Failed instead, with `callEndReason` `outside_calling_hours`. A queued call cannot be cancelled yet. To have the API refuse these calls instead, send `reject_outside_hours: true`.

If our servers can't start a call the API accepted, for example because its call flow was deactivated after the request, the call is marked Failed in Call History. Its `status` is `failed`, `callEndReason` gives the reason, such as `no_active_call_flow`, and `error` explains it. These calls do not trigger `callback_url`. A system error while the call is connecting can leave it Scheduled instead.

To check on a call, read its record with [Get a Specific Call History](/v1/api-reference/endpoints/calls/call-history/get) using the `callId` from the response.



### Response Fields

<ResponseField name="status" type="string">
  The status of the request, indicating the success or failure of the call initiation.
</ResponseField>

<ResponseField name="message" type="string">
  A message providing feedback about the call initiation process, typically confirming successful initiation or describing an error.
</ResponseField>

<ResponseField name="call_agent_id" type="string">
  The agent the call was placed with. Useful when you sent a `call_flow_id` and want to confirm which agent it resolved to.
</ResponseField>

<ResponseField name="callId" type="string">
  A unique identifier assigned to the initiated call. This ID can be used to track the call's progress or retrieve its details later.
</ResponseField>

<ResponseField name="roomName" type="string">
  The name of the session room created for this call session.
</ResponseField>

<ResponseField name="jobId" type="string">
  The identifier of the background job scheduled to execute the outbound call.
</ResponseField>

<ResponseField name="error" type="string">
  Returned when the call could not be initiated. Explains why, in text you can show to your users. Some 400 responses have no `error` and give the reason in `message` instead: a missing field, a field of the wrong type, or a `call_agent_id` and `call_flow_id` that refer to different agents.
</ResponseField>

<ResponseField name="code" type="string">
  Returned with some errors, so you can handle them in code:

  - `OUTSIDE_CALLING_HOURS` (409): the call flow is outside its calling hours and you sent `reject_outside_hours: true`.
  - `NO_ACTIVE_CALL_FLOW` (422): the agent has no live call flow. Use an agent whose call flow is live.
  - `CALL_FLOW_INBOUND_ONLY` (422): the agent's call flow only takes inbound calls.

  With these codes, no call is queued and nothing is added to Call History.
</ResponseField>

<ResponseField name="next_available_at" type="string">
  Returned with `OUTSIDE_CALLING_HOURS`. When the call flow's next calling window opens, as an ISO 8601 time in UTC. It is `null` when there is no calling window in the next 30 days.
</ResponseField>

<ResponseField name="timezone" type="string">
  Returned with `OUTSIDE_CALLING_HOURS`. The time zone of the call flow's calling hours, such as `America/New_York`, or `null` if the call flow has no time zone set.
</ResponseField>

```json Personalized greeting and voicemail
  "to": "+1234567890",
  "call_agent_id": "a1b2c3d4e5f6a7b8c9d0e1f2",

  }
}
```
</RequestExample>
