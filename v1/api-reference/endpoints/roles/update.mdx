---
title: "Update Role"
api: "PUT /v1/api/roles-and-permissions/roles/{roleId}"
description: "Update an existing role's name, description, permissions, or assigned users."
---

Requires the `role:edit` permission in the workspace.

## Headers
<ParamField header="x-workspace-id" type="string" required>
Workspace identifier for the API.
</ParamField>

## Path Parameters

<ParamField path="roleId" type="string" required>
The unique identifier of the role to update.
</ParamField>

## Request Body

<ParamField body="name" type="string">
Updated name for the role.
</ParamField>

<ParamField body="description" type="string">
Updated description for the role. Must not be empty.
</ParamField>

<ParamField body="permissions" type="array of strings">
The complete new set of permission keys, in `category:action` form (e.g., `"agent:view"`). This replaces the role's permissions; it is not merged with them. At least one key is required when the field is sent. Use [List Permissions](/v1/api-reference/endpoints/roles/list-permissions) for the available keys.
</ParamField>

<ParamField body="userIds" type="array of strings" required>
User IDs to assign this role to, in addition to the users who already hold it. Send `[]` to assign no one new.

<Warning>
  Always send `userIds`. If it is omitted, the other changes are saved but the request returns `500 Internal server error`.
</Warning>
</ParamField>

<Note>
  For the built-in system roles (`owner`, `admin`, `editor`, `viewer`), only `userIds` is applied. The name, description and permissions of a system role can't be changed.
</Note>

## Response

<ResponseField name="_id" type="string">
Unique identifier for the role.
</ResponseField>

<ResponseField name="name" type="string">
Updated name of the role.
</ResponseField>

<ResponseField name="description" type="string">
Updated description of the role.
</ResponseField>

<ResponseField name="permissions" type="object">
Permissions grouped by category, as in [Create Role](/v1/api-reference/endpoints/roles/create).
</ResponseField>
